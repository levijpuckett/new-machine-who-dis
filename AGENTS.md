# Global preferences

## Writing

Do not use the em dash in your writing. Use other forms of punctuation in place of them
wherever you can. If you must use a dash, use "-" in place of the real em dash.

## Python package management

Always use virtual environments (`python -m venv` etc.) when installing Python
packages. Never use `pip install --break-system-packages`.

## Plan mode

In plan mode, always use the plan-studio skill instead of the terminal
AskUserQuestion tool or plain-text plan review:

- Any time you would otherwise call AskUserQuestion while in plan mode -
  before drafting the plan, or while refining it - invoke plan-studio's
  questions mode instead.
- Before calling ExitPlanMode, always invoke plan-studio's review loop.

## Commit messages
Commit messges should be succinct. Follow this format:

```text
Short (72 chars or less) summary

More detailed explanatory text. Wrap it to 72 characters. The blank
line separating the summary from the body is critical (unless you omit
the body entirely).

Write your commit message in the imperative: "Fix bug" and not "Fixed
bug" or "Fixes bug." This convention matches up with commit messages
generated by commands like git merge and git revert.

Further paragraphs come after blank lines.

- Bullet points are okay, too.
- Typically a hyphen or asterisk is used for the bullet, followed by a
  single space. Use a hanging indent.
```

Do not add more information than necessary, don't describe the "how" unless it's not obvious.
Focus on the "why", but only where it's not obvious from the context of the code changes.

## Code documentation

Less is more.

NEVER describe previous state in code comments - only describe what the code does *now* and
*why*. Keep comments short: lay out contracts, gotchas, describe tricky bits of the source,
and briefly outline important design components when it really matters.

## Code review

When running the code-review skill, also apply the claudy-comment-detector
skill to the same target and merge its findings into the review's output.

## Understanding checks

At logical gates (wrapping up a task, the code review cycle, before a push
or PR), run the understanding-check skill on the change before moving on.
